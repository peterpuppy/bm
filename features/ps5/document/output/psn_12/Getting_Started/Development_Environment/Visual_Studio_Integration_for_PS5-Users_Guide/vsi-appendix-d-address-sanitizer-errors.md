# Visual Studio Integration for PlayStation®5 User's Guide Appendix D - Address Sanitizer Errors

| **Error** | **Description** |
| --- | --- |
| `__sanitizer_get_allocated_size() not owned` | `__sanitizer_get_allocated_size()` is a function provided by ASan to return information about memory that was allocated using its allocator. Any program that was compiled with Asan support will be using this allocator. This function will return the size of the memory allocated for the particular address passed in. If an address is passed which was not allocated with the allocator (for example a stack address), or the address passed is not the first memory location of a chunk, then this error will be reported. |
| `Alloc-type mismatch` | ASan will report this error when a heap-allocated address is deallocated using a mismatched mechanism.  For example `free()` should be paired with `malloc()`, `delete`with `new`, and `delete[]` with `new[]`. If these pairings are not used, for example the program tries to deallocate a `malloc()`-allocated address with delete, this error will be reported. |
| `Bad parameters to __sanitizer_annotate_contiguous_container()` | The `__sanitizer_annotate_contiguous_container()` function is provided by the ASan library to enable the user to supply information about containers to the allocator. This information can be used to determine when memory that has been allocated correctly to a container, but not yet assigned to a particular value, is being used.  As an example, consider `std::vector<T>::reserve()`. This lets the container allocate memory for the future, but the memory itself remains uninitialized and is not valid for use. The `__sanitizer_annotate_contiguous_container()`function provides ASan with information about the reserved memory in a container as it updates. An error of this type denotes that the user has called the annotation function with incorrect parameters. |
| `Container overflow` | As described in the [Bad parameters to \_\_sanitizer\_annotate\_contiguous\_container()](vsi-appendix-d-address-sanitizer-errors.html#visual-studio-integration-for-ps5-users-guide_9__0bad_params_sanitizer) error, ASan can annotate containers and detect when reserved but uninitialized memory is being used. This error denotes that scenario. |
| `Double free()` | A `double free()` error is reported when a memory address is passed to the `free()` function multiple times. After a piece of memory allocated via `malloc()` has been `free()`'d once, it is not valid to pass the same address to `free()` it again. |
| `Dynamic stack buffer overflow` | Dynamic stack buffers are created using `alloca()`. If a program writes to a memory region immediately after the limit of such a buffer, this error will be reported. |
| `free() not malloc() -ed` | If an address passed to `free()`was not allocated with `malloc()`, ASan will report this error. The previous `Alloc-type mismatch` error takes precedence over this error in the cases where the address was allocated on the heap by a method other than `malloc()`. |
| `Global buffer overflow` | ASan will report this error when the memory region after a static (global) buffer has been accessed. |
| `Heap buffer overflow` | This happens when the program writes to the memory region after the end of a heap-allocated buffer. |
| `Heap use after free` | The program has attempted to use an address that was previously heap-allocated, but has been deallocated. |
| `Initialization order fiasco` | Global static data can be initialized with functions. This happens before `main()` and the order these functions are run is not guaranteed. If an initialization function refers to another piece of static data, there is no guarantee that it has been initialized yet. This error alerts the user of such a problem in their program. For more information, refer to <https://isocpp.org/wiki/faq/ctors#static-init-order>. |
| `Intra-object overflow` | This happens when an object contains a buffer and a memory access overflows the buffer into another member. Consider:   ``` struct A { char buffer[1]; int member; }; ```   Using the expression `buffer[1]` will overflow into the next member of the object. |
| `Invalid pointer pair` | An invalid pointer pair error arises when pointers which are not in the same allocated block are compared or used together in pointer arithmetic. |
| `Negative-size parameter` | Some CRT functions take size parameters, for example, `strncpy()`.  For these functions it is not possible to supply a negative size because the parameters use unsigned types. However, due to implicit casting, an unsigned representation of a negative value can accidentally be supplied to one of these functions, which will typically be interpreted as a very large number by the function.  This category of error is for detecting such cases where a negative size has been accidentally passed to a CRT function. |
| `New-delete size mismatch` | C++14 introduced sized `delete` operators (refer to <http://en.cppreference.com/w/cpp/memory/new/operator_delete> for details). This error detects when a sized `delete` operator is called for an address which was allocated with a different size than that which was provided to the `delete` operator. |
| `Parameter overlap` | Some CRT functions have restrictions that you cannot pass overlapping memory regions into their arguments.  The reason for this can be illustrated by looking at `strcpy` as an example. If the source of the copy is a few bytes behind of the destination, then the source could be changed before it is copied into the destination, for example:    This error type will detect when overlapping memory regions are passed to affected CRT functions. |
| `Stack buffer overflow` | If the program tries to write to the memory region after a stack-allocated buffer, this error is produced. |
| `Stack buffer underflow` | If the program tries to write to the memory region before a stack-allocated buffer, this error is produced. |
| `Stack overflow` | A stack overflow happens when the stacks of the program grow too large or numerous. When this occurs, the program can overflow the space allocated for the stack. Typically this will happen because of a recursive function that is nested too deeply, or because of large amounts of data being allocated on the stack with `alloca()`. |
| `Stack use after return` | A stack address can only be used in the function whose stack it was allocated on. Attempting to use a stack address after a function has returned will result in this error. |
| `Stack use after scope` | If a memory address that belongs to a variable in a scope that has ended is accessed, this error is reported by ASan. This can happen when, for example, a pointer is taken to a local variable declared in a lexical scope. |
| `Use after poison` | Memory regions can be manually poisoned using the `__asan_poison_memory_region()` function. ASan will report this error if a program accesses a memory poisoned in this way. |
| `Bad parameters to __sanitizer_copy_contiguous_container_annotations()` | You can manually annotate memory regions with the `__sanitizer_annotate_contiguous_container()` function. If such a region is copied, the ASan annotations will not be copied with it. To carry forward any annotations, you must use the `__sanitizer_copy_contiguous_container_annotations()` function instead. ASan will report this error if the call to this function contains invalid parameters. For example, an address range which does not represent an annotated memory region. |
