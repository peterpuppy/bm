# Clang Static Analysis

The integration for Clang’s Static Analysis comprises of two visual elements:

* A new Visual Studio Tool Window called the [Issues Window](using-the-visual-studio-issues-window.html).
* [Corresponding annotations](source-code-annotation-of-issues-from-the-issues-window.html) shown in the source code for the projects that have been analyzed.

# Using the Visual Studio Issues Window

The **Issues Window** is used to show the results of performing a Static Analysis build on the currently loaded Solution, individual projects or source files. It also provides an [Analyze Menu](using-the-visual-studio-issues-window.html#visual-studio-integration-for-ps5-users-guide_5_1__section_bv3_kzp_ygc) used to initiate Static Analysis builds, and options to filter the results.

To open the Issues Window:

* In the **View** menu, select **Other Windows**, then click **Issues Window.**

The **Issues Window** shows the results of the Static Analysis build on the loaded Solution.

Tooltips are available for some issues by rolling the mouse pointer over the Issues List entries.

## Analyze Menu

The Analyze menu on the **Issues Window** enables you to perform a full Static Analysis build of the whole Solution, or just individual projects. Any previous state of a normal build will be left intact by any analysis.

Note:

If SN-DBS or IncrediBuild support is available, it will be used to speed up the analysis.

To perform a Static Analysis build:

1. Click the **Analyze** button.
2. **Select Solution** to build the whole solution, or choose a specific project from the drop-down list.

Once a build is in progress, issues found by Clang will start to be shown in the **Issues Window**.

The settings used by Clang for the analysis can be configured for projects and individual files in the Static Analyzer C/C++ section in the Project Properties dialog. Refer to [Static Analyzer](vsi-project-settings-c-c-plus-plus.html#visual-studio-integration-for-ps5-users-guide_2_2_5__section_ify_hqq_ygc) for more information.

# Performing a Static Analysis Using the Visual Studio Solution Explorer

Static Analysis can be performed for a subset of source files within a project rather than the project as a whole.

To perform Static Analysis on individual files:

* In **Solution Explorer**, right-click the source files, and then click **Run Clang Static Analyzer**.

# Suppressing Issues Generated by Static Analysis

Issues generated by Static Analysis can be individually suppressed to prevent them being shown in future.

To suppress an issue:

* In the **Issues Window**, select the issue to suppress, then right click, and click **Suppress**. When an issue has been chosen for suppression, it will be initially shown grayed out in the Issues Window along with its annotations in the source view.

To reverse a suppressed issue:

* In the **Issues Window**, select the suppressed issue, then right-click, and click **Restore.**

When you have finished choosing which issues to suppress, you can commit these changes by clicking **Save Suppressions** on the [Options](visual-studio-issues-window-options.html) menu on the **Issues Window** dialog. At this point the suppressed issues will no longer be shown.

Note:

You can also suppress multiple issues by selecting source file or project nodes in the **Issues Window**.

During an Analysis build, hashes are created by Clang to identify specific diagnostic messages that are then shown in the **Issues Window**. Suppression works by matching the hashes for previously suppressed issues against those seen in later Analysis builds. The suppressed hashes are saved to a file alongside the `.sln` file for the loaded Solution. This file has a `.csa-suppress.json` extension and is in the text JSON format. It can be safely stored and shared with others using a source control system.

Issues can share the same hashes. This happens when the fault reported by the Analyzer originates within a header file. Because of this, suppressing an issue can result in other issues also being suppressed when source files `#include` the same header file.

# Visual Studio Issues Window Options

The **Options** menu provides the following functionality:

| **Option** | **Description** |
| --- | --- |
| **Group by Category** | By default, the Issues list will show issues grouped by the location of originating source files within their projects, and the location button will be highlighted. Enable this option to show issues grouped by the category of issue instead. |
| **Auto Expand Issues** | If selected, any issue containing multiple steps will be fully expanded in the **Issues Window** so that all steps are visible. If this option is not selected, the issue will be displayed collapsed so that the steps are not automatically visible. |
| **Show Source Annotations** | Normally, open source files will be annotated to show the descriptions for current issues. Disable this option to hide source annotations. |
| **Use Distributed Build System** | If SN-DBS or IncrediBuild support has been installed, it can be used during an Analysis build to speed things up. Disabling this option will result in all analysis builds being done wholly on the local PC. |
| **Show All Suppressions** | When an issue has been suppressed, it will be removed from the Issues Window when the **Save Suppressions** option is selected, and the current suppression choices are saved. However, if this option is enabled, all issues found by the Analyzer will be displayed, whether they are suppressed or not. Suppressed issues will be shown grayed out during the subsequent Analysis build. This feature enables you to restore previously suppressed issues. |
| **Save Suppressions** | Click to save any issues that have been selected for suppression. The hashes for any suppressed issues will now be saved to the suppression JSON file. Suppressed issues will then be removed from the Issues Window, unless **Show All Suppressions** is enabled. |
| **Clear All Suppressions** | Click to remove all set suppressions from the **Issues Window**. |

# Filtering the Issues List in the Visual Studio Issues Window

The Issues list can be filtered by project, category of issue or free text. Issues that have been removed through filtering will also remove any source code annotation.

To filter by Project:

1. Click the **All Projects** drop-down list.
2. Check any projects you want displayed, or check **All Projects**.
3. Uncheck any projects you do not want displayed, or uncheck **All Projects**.

To filter by Category:

1. Click the **All Category** drop-down list.
2. Check any categories you want displayed, or check **All Categories**.
3. Uncheck any categories you do not want displayed, or uncheck **All Categories**.

To filter by free text:

* Begin typing the search term in the **Search** text box.

As the text is typed, the Issues list is filtered automatically to those that contain the text within the issue description, category, source file name, project name or name of the originating 'checker'.

# Source Code Annotation of Issues from the Issues Window

Open source files will be automatically annotated to display the description for any issue shown in the **Issues Window**. The origin of the message will be indicated with a caret, with optional underlining of the contributing expression.

The annotation for the currently selected issue in the **Issues Window** will be shown with a highlight.

To view corresponding code annotations from issues:

* Clicking on an issue in the **Issues Window** will open the source window with the corresponding annotated code aligned to the center of the screen.
* Double-clicking on an issue in the **Issues Window** will move the focus to the editor to enable immediate text editing.

To view corresponding issues from code annotations:

* Clicking on an annotation will select the corresponding issue in the **Issues Window**.

The source view will scroll to place the line for the annotation in the middle of the view.

Where more than one issue has been generated by the same line of source code, a drop-down list is provided on the annotation to enable selection of the other annotations.

## Multiple-Step Annotations

If an issue is comprised of multiple steps, double-clicking the issue annotation will remove other annotations in the file and show each step as a separate numbered annotation.

Step annotations provide navigation arrows to jump to previous and next steps in sequence. Double clicking on a step annotation will collapse all steps and reposition the view to the top level annotation.

## Editing Annotated Source Code

Editing the text within a source file that has been annotated will update the annotation to indicate that it is ‘dirty’ by changing its color to grey. Reverting the changes will reinstate the annotation as it was.

## Integrating Clang Static Analysis with Custom Builds

You can get Static Analysis results for standard executable and library project configurations by selecting **Analyze** from the **Issues Window**. This performs a partial build for those projects, but with Clang invoked to do analysis using `--analyze` rather than compilation. Along with `-Xclang -analyzer-output=plist-multi-file`, plist files are then created, which are processed and the results passed back to Visual Studio.

For custom builds using Makefile project configurations, no automatic Analysis build can be done when **Analyze** is selected. However, the project file directory for any Makefile project will be checked for plist files. If any plist files are found, they will be processed in the same way as for normal executable and library projects, with their results added to the Issues Window and the source opened in the editor.

It is possible to provide a command line to be invoked for a Makefile project during an Analysis build, as well as specifying the location to find the plist files generated. As this requires editing projects files, some familiarity with MSBuild is recommended.

## Modifying a Makefile Project for Static Analysis Builds

A new property called `NMakeClangAnalyzeCommandLine` needs be added to the project file for all project configurations that are built for the project.

To add an `NMakeClangAnalyzeCommandLine` property:

1. Open the `.vcxproj` file for the project, and locate the **PropertyGroup** sections that contain the current NMake specific properties. These will be typically conditional on a specific project configuration, for example **Debug|Prospero**, and contain properties specifying build command lines, such as `NMakeBuildCommandLine`.
2. Add your new `NMakeClangAnalyzeCommandLine` property to this group. The property value should specify one or more command lines needed to generate a .plist file for all the source files that are to be analyzed.
3. If you wish to specify a specific location to look for the .plist files rather than the project’s directory, also add a property called `PlistDir` to the same property group.

The example below modifies the Debug configuration to call the current batch file with a new target analyze when Analyze is selected in the Issues Window. The .plists files will be expected in the directory called **Plist** in the project’s directory.

```
<PropertyGroup Condition="'$(Configuration)|$(Platform)'=='Debug|Prospero'">
  <NMakeBuildCommandLine>Prospero.bat build</NMakeBuildCommandLine>
  <NMakeCleanCommandLine>Prospero.bat clean</NMakeCleanCommandLine>
  <NMakeClangAnalyzeCommandLine>Prospero.bat analyze</NMakeClangAnalyzeCommandLine>
  <PlistDir>$(ProjectDir)Plist</PlistDir>
</PropertyGroup>
```
