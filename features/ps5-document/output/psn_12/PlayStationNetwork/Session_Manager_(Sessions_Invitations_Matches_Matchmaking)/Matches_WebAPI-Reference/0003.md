# Matches

# createMatch

Create matches

### Description

This request can be used to create matches. Matches can be individually created for each multi-play session; however, the application developer can arbitrarily define which section in the game to assign as one match.

**Activities**

To create a match, a link with an activity must be made. The link with an activity indicates which specific game mode a match consists of.  
  
The activity to link must be defined in advance as a PlayStation™Network object. If an activity that hasn't been defined is specified, the match can't be created and an error will occur.

The activity type will be checked upon creating a match. The types of activities supported by the Matches Web API are as follows. If any other activity is specified, the match can't be created and an error will occur.

* *isOnlineMultiplay* = false and *category* = Competitive
* *isOnlineMultiplay* = true and *category* = Competitive, Progress, or Open Ended

The following three parameters for a match will be automatically determined based on the activity definition:

* *groupingType*: The method of grouping users together within the match  
  If the value of *isTeamActivity* is true for the activity, *groupingType* is TEAM\_MATCH (a match played in teams). Otherwise, the match is NON\_TEAM\_MATCH (a match played among individuals).
* *competitionType*: Play type of the match  
  If the value of *category* is Competitive in the activity, the *competitionType* is COMPETITIVE (competitive play). Otherwise, the match is COOPERATIVE (cooperative play).
* *resultType*: Result type of the match  
  If a value for *scoreStatistics* exists in the activity, the *resultType* is SCORE (with the results including rankings and scores). Otherwise, the type is RESULT (with the results including only rankings).

Linking with activities is performed when matches are created, and linkages cannot be modified afterward.

**Match status**

When a match is created, its status automatically becomes WAITING. WAITING indicates a status in which a match is waiting for participants to register.

**In-Game Rosters**

Players or teams to participate in a match can be specified as *inGameRoster* when a match is created. Even if the players or teams to participate in a match aren't specified when a match is created, they can be reported at any time, up until the match completes. However, at least one player or more must be registered before the match is started. In addition, if *groupingType* is TEAM\_MATCH, at least one team or more must be specified before the match is started.  
When setting a team and registering team members, the team members must also be registered as players at the same time.

**The status and availability of a child activity (task/sub task)**

When *competitionType* is COOPERATIVE, the status and availability of a child activity (task/sub task) belonging to the activity linked to the match can be reported after the match is started. When a match is created, the status of all child activities will be set to WAITING and the availability will be set to UNAVAILABLE. Both can be updated using [updateMatchDetail](0004.html) after the match is started.

**Example Request**

```
POST {baseUrl}/v1/matches
{
  "npServiceLabel": "0",
  "activityId": "XXXXXXXX",
  "zoneId": "XXXX",
  "expirationTime": 60,
  "cancellationTime": 600,
  "customData": "4b2bc611-e149-464c-97db-76ddc8935255",
  "inGameRoster": {
    "players": [
      {
        "playerId": "1",
        "playerType": "PSN_PLAYER",
        "playerName": "Tank 1",
        "accountId": "1234567891"
      }
    ],
    "teams": [
      {
        "teamId": "1",
        "teamName": "Team Fang",
        "members": [
          {
            "playerId": "1"
          }
        ]
      }
    ]
  }
}
```

**Example Response**

```
{
  "matchId": "58aa8318-d5a6-11e8-9f8b-f2801f1b9fd1"
}
```

# updateMatchDetail

Update match details

### Description

Match details can be updated with this request.  
  
This request partially updates match details. In other words, only the properties specified in the request are updated.  
Note that properties cannot be deleted.

**Match Statuses Supported by This Request**

Match details can only be updated with this request if the match status meets one of the following conditions.

* The match status is WAITING
* The match status is PLAYING
* The match status is ONHOLD

Details of a match whose status is COMPLETED or CANCELLED can't be updated.

**Match Validity Period**

If a match is left alone for more than a certain amount of time, it will automatically be transitioned to the CANCELLED status based on *expirationTime* and *cancellationTime*.

* For WAITING: If the match is left alone from when it entered the WAITING status until *expirationTime* elapses
* For PLAYING: If the match is left alone from when it last entered the PLAYING status until *cancellationTime* elapses
* For ONHOLD: If the match is left alone from when it last entered the ONHOLD status until *expirationTime* elapses

Specify *expirationTime* to update this validity period.  
You can reset the timer by updating *expirationTime* while the status is WAITING or ONHOLD.

**In-Game Rosters**

Information of players or teams in an in-game roster can be updated by specifying *inGameRoster*.  
The players/teams specified with *inGameRoster* will join the match. If a player/team not previously included in the in-game roster is specified with *inGameRoster*, that player/team will now be joined in the match. Meanwhile, if a player/team that was included in the in-game roster is not specified in *inGameRoster*, the player/team will be removed from the match.  
However, the removed player/team will not be deleted from the in-game roster. The participation status (joinFlag) will change, but the player/team will remain in the in-game roster as part of its history.

joinFlag has two types.  
- The player's participation status in the match  
- The player's participation status in a particular team

If a player moves between teams, the participation status for the original team becomes false as that for the new team becomes true.

Combining currently participating players and players left in the history, a maximum of 500 players can be registered for a match. Similarly, combining currently participating teams and teams left in the history, a maximum of 200 teams can be registered for a match. An error will occur if either of these maximum values is exceeded.

It is recommended you only update the in-game roster with this request when you want to update the in-game roster overall, such as when some players newly join while others leave the match at the same time or when a new team is added. Use [joinMatch](0006.html)/[leaveMatch](0007.html) when individual players join/leave the match. However, use this request in situations such as when the representative who had been controlling the match leaves, and it is not possible to track individual players/teams joining/leaving the match within the time it takes for a new representative to be selected.

**Results (Interim Progress)**

Interim progress of the match can be reported by specifying *matchResults*.  
However, you can only report the interim progress of a match with this request if the match's *competitionType* is COMPETITIVE. Interim progress can't be reported if the match's *competitionType* is COOPERATIVE.  
Every time an interim progress is reported, any and all previously reported interim progress will be overwritten.

The format in which results are to be reported differs depending on the match's *groupingType*.

* *playerResults* must be specified if *groupingType* is NON\_TEAM\_MATCH. Specify player rankings in *playerResults*. If the match's *resultType* is SCORE, player scores must also be specified.
* *teamResults* must be specified if *groupingType* is TEAM\_MATCH. Specify team rankings in *teamResults*. If the match's *resultType* is SCORE, team scores must also be specified.  
  You can also specify each player's score (degree of contribution to the team) as an option.

Specify a value as follows for score when *scoreStatistics* is defined in the activity that corresponds to the match.

* Specify a positive integer value in milliseconds when *displayFormat* of *scoreStatistics* is time.
* Specify an integer value when *displayFormat* of *scoreStatistics* is numeric. Note that by specifying the number of digits after the decimal point in *decimalPlaces* of scoreStatistics, it is possible to display decimal scores on the system software.

The players/teams to include in the results must be registered in advance with the in-game roster or registered within the same request. Results of players/teams that have left the match can also be included.  
It's not necessary to include the results of all players/teams registered in the in-game roster; however, all interim progress results registered in the past of players/teams that aren't specified will be overwritten and deleted.  
Only the results of the players and teams reported in this request will be displayed on the system software screen for displaying match results.

**How to Specify Rankings**

Rankings are specified as follows, based on the type of competitive play.

* For a many vs many match: Specify each player or team's ranking as-is, as in 1, 2, 3... It is also possible to specify the same ranking to multiple players/teams as in 1, 1, 3, and so forth.
* For a one vs one match: Specify first place for the winning player/team and second place for the losing player/team in the rankings. In the case of a tie, give first place to both.

**Child Activities (Tasks/Sub Tasks)**

The status and availability of child activities (tasks/sub tasks) belonging to the activity linked to the match can be updated by specifying *childActivities*. *childActivities* can only be specified when all of the following conditions are satisfied.

* The match's *competitionType* is COOPERATIVE.
* The match status is PLAYING.

The status and availability of a child activity that wasn't specified in *childActivities* won't be updated.

**Child Activity Status (Progress)**

The status of a child activity can be updated be specifying *status*. The match's progress can be updated by updating the child activity status. The progress status of a match entailing cooperative play is calculated based on the child activity status.  
Upon creation of the match, *status* of all child activities will be set to WAITING. The status of child activities has three types: WAITING, PLAYING, and COMPLETED. Updates can only be made to transition from left to right in this order. An update that makes a status go back (right to left) from the current status can't be performed.  
A sub task can only be updated if the parent task's status is already PLAYING or when the parent's task is being updated from WAITING to PLAYING or COMPLETED.  
The status of sub tasks can be updated at the same time the status of a parent task is updated.

**Child Activity Availability**

The availability of a child activity can be updated by specifying *availability*. The display or lack of display of the player's child activities can be controlled by updating the child activity availability.  
Upon creation of the match, *availability* of all child activities will be set to UNAVAILABLE. A child activity will be displayed in the system software if its *availability* is set to AVAILABLE and won't be displayed if UNAVAILABLE is set.

# updateMatchStatus

Update the status of a match

### Description

The status of a match can be updated using this request.  
The status of a match can't be updated it is has already transitioned to COMPLETED or CANCELLED.  
A match will automatically be canceled after a certain time passes while its status is WAITING, PLAYING, or ONHOLD.

**Status**

* **PLAYING**

  Because the status of a match upon its creation is WAITING, it must be updated PLAYING when gameplay commences. Changing the status to PLAYING indicates that the match has started or resumed. Therefore, the following checks are performed when the status is changed to PLAYING. The status can't be changed to PLAYING if these conditions aren't met.

  + At least one player must be in the *inGameRoster*
  + If *groupingType* is TEAM\_MATCH, at least one team must be in the *inGameRoster*

  *matchStartTimestamp* is recorded the first time the status of a match becomes PLAYING.
* **ONHOLD**

  Changing the status to ONHOLD means temporarily pausing the match. *lastPausedTimestamp* is recorded every time the status of a match becomes ONHOLD.
* **CANCELLED**

  Changing the status to CANCELLED means canceling the match. *matchEndTimestamp* is recorded the first time the status of a match becomes CANCELLED.

**Match Validity Period**

If a match is left alone for more than a certain amount of time, it will automatically be transitioned to the CANCELLED status based on *expirationTime* and *cancellationTime*.

* For WAITING: If the match is left alone from when it entered the WAITING status until *expirationTime* elapses
* For PLAYING: If the match is left alone from when it last entered the PLAYING status until *cancellationTime* elapses
* If ONHOLD: If the match is left alone from when it last entered the ONHOLD status until *expirationTime* elapses

However, you can reset the timer by updating *expirationTime* while the status is WAITING or ONHOLD. *expirationTime* can be updated using [updateMatchDetail](0004.html).

**Example Request**

```
PUT {baseUrl}/v1/matches/{matchId}/status

{
  "npServiceLabel": "0",
  "status": "PLAYING"
}
```
